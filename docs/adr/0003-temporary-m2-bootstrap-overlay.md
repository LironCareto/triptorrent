# ADR 0003: Temporary M2 bootstrap overlay

Status: accepted for prototype

## Context

M2 must demonstrate membership, content discovery, relay selection, leases, reconnects and churn without prematurely choosing the decentralized and privacy-preserving discovery design reserved for M3.

## Decision

Add one `triptorrent-overlay` crate containing an in-memory registry, a temporary TCP request/response bootstrap, leased peer/content and relay advertisements, queued route assignments and a deterministic simulation harness. The bootstrap selects the lexicographically first live provider and relay. Failed relays can be reported and removed so discovery selects an alternative.

Providers use process-lifetime X25519 keys generated by `snow`. The experimental peer ID is the BLAKE3 digest of the public key. M2 sessions use the reviewed `Noise_KN_25519_ChaChaPoly_BLAKE2s` pattern: the provider proves possession of the advertised private key and the receiver obtains its public key through discovery. Existing M1 relay framing and file messages remain unchanged.

## Alternatives considered

A DHT was rejected because M3 exists to evaluate decentralized discovery, metadata leakage and eclipse/Sybil risks. Continuing to require a manually shared M1 PSK would prevent a receiver from using only the bootstrap address and content ID. Having the bootstrap distribute a symmetric session key would expose every session key to it, so an ephemeral provider public key was preferred.

## Consequences

The prototype can exercise multiple peers and relays, expiry, reconnect and failover locally. It adds a centralized point that sees content metadata and topology. Bootstrap messages are unauthenticated; a malicious bootstrap can replace provider keys, forge state or remove relays. Selection is deterministic rather than load- or privacy-aware. All M2 formats, identities, lease values and policies are experimental and expected to change through RFC work and M3 research.
